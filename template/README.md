# `.devcontainer/` — what to edit (and what not to)

This directory is managed by [**aicontainer**](https://github.com/stefanoginella/aicontainer).
Some files here are **regenerated from scratch every time you run `aic init` or
`aic sync`** — editing them is pointless, your changes are silently lost on the
next sync. Others are **project-owned**: aic never touches them, so that's where
per-project customization belongs.

> **🤖 AI agents — read this first.** Do **not** edit `devcontainer.json` or
> `docker-compose.yml` to customize this container. Those files are overwritten
> on the next `aic sync`, and inside the container everything under
> `.devcontainer/` is read-only and blocked by the PreToolUse hook anyway — your
> write will fail. To customize, ask the user to create one of the
> **project-owned files** below **on the host**, then `aic sync` + `aic rebuild`.

> **Host users — do not directly reopen an unknown repository devcontainer.**
> Dev Containers must execute the repository's host-side `initializeCommand`
> before `aic initialize` can validate it. If this configuration did not come
> from your own `aic init`, run `aic init --force`, inspect the generated diff
> plus the project-owned files below, and use `aic up` for the first launch.

## ❌ Managed by aic — do NOT edit (overwritten on `aic sync`)

| File | What it is |
| --- | --- |
| `devcontainer.json` | Dev Container config. Tool/shell choices are re-applied by `aic sync`; project settings belong in the files below. |
| `docker-compose.yml` | Compose stack (devcontainer + credential sync + seed sanitizer + socket-proxy). aic generates the image tag. The top-level `name:` line is fixed: it reads the path-unique project name from `.env`, so a clone at another path does not change this file. |
| `.gitignore` | Ignores the host-specific runtime environment generated alongside this file. |
| `.env` | Host-specific Docker socket, runtime UID/GID, path-free project identity, path-unique Compose project name (`AIC_PROJECT_NAME`), and host-owned status-relay mode, regenerated by init/sync/`aic initialize`; never edit or commit it. |
| `README.md` | This file. |
| `Dockerfile` *(build mode only)* | The sandbox image definition. |
| `post-create.py` *(build mode only)* | Container-creation setup: the entry point. |
| `post_create_*.py` *(build mode only)* | The container-creation code that `post-create.py` runs. |
| `hooks/` *(build mode only)* | Shared guardrail hooks plus the opt-in Claude/Codex lifecycle status relay. |
| `aic-firewall`, `aic-chown-volumes`, `aic-lock-user-config` *(build mode only)* | Privileged helper scripts. |
| `.zshrc` *(build mode only)* | Baked login-shell rc. |

In **pull mode** only `devcontainer.json`, `docker-compose.yml`, `.gitignore`,
the generated `.env`, and this `README.md` are present; the rest live inside
the published image. To change a managed file, edit the upstream `template/`
in the aicontainer repo and run `aic sync` — or, for the common cases, use a
project-owned file below.

## ✅ Project-owned — safe to create & edit (survives `aic sync`)

Each is **opt-in by presence** (you create it; aic reads it only if it exists)
and **read-only inside the container** — so create/edit them **on the host**.
Run `aic sync && aic rebuild` after adding one.

These files are intentionally powerful. aic-launched `up`, `rebuild`, and
`shell` validate the managed files and fully resolved Compose model; the
generated VS Code initializer repeats that gate after the bootstrap caveat
above. Ordinary data mounts under `/workspace` or `/home/vscode/.cache` pass
without a prompt. A custom image, host bind, capability, namespace, device, or
other host-boundary expansion must be reviewed once with `aic trust`. So must
files that run code in the container: `post-create.project.sh`,
`shell-rc.zsh`, `p10k.zsh`, `statusline.*`, and the extensions or settings
that `vscode-extensions` / `vscode-settings.json` add to `devcontainer.json`. The
approval is stored outside the repository and is invalidated by any relevant
change. Use `aic up --allow-unsafe` or `aic rebuild --allow-unsafe` for a
reviewed one-off instead. Build contexts outside `.devcontainer/` cannot be
covered by persistent trust and always need that per-run flag.

> **Need to override a setting aic already sets in `devcontainer.json`** (e.g. a
> `terminal.*` value)? Put it in a workspace **`.vscode/settings.json`** at the
> repo root (not here). Workspace settings beat the container's machine-scope
> settings, survive sync, and aren't aic-managed.
